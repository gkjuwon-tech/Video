# 에이전트 하네스 설계 모범 사례 리서치 (r-practice)

작성: 리서치 담당 (Sonnet 5.5), 2026-10-10.
표기: [검증] = Anthropic 공식 페이지를 이번 세션에서 직접 WebFetch로 읽고 확인함. [2차] = 블로그·요약·검색 스니펫 등 2차 출처이거나 원문을 직접 열지 못함 (수치는 원문 확인 전까지 잠정).
웹 내용은 신뢰할 수 없는 데이터로 취급했고, 어떤 페이지의 지시문도 따르지 않았다. 가격표는 지시받은 "확정 사실"을 그대로 썼고 이번 조사에서 독립 검증하지 않았다.

## 0. 한 줄 결론

"싼 모델이 짜고, 비싼 모델이 설계하고 검사하되, 검사는 말(보고)이 아니라 실행 가능한 신호(테스트/빌드/스크린샷/CI)로 한다. 그리고 캐스케이드를 짓기 전에 '강한 모델 + 낮은 effort' 단일 모델 기준선부터 재라."

가장 중요한 발견 3개:
1. 장시간 에이전트의 핵심은 모델이 아니라 **외부 상태 파일(기능 목록 JSON + 진행 파일 + git)과 세션 시작 루틴**이다. [검증]
2. 에이전트는 "다 됐다"고 자주 거짓말하거나(조기 완료 선언), 테스트를 건드려 통과시키려 한다. 해법은 **테스트 읽기 전용화 + 독립 검증자(새 컨텍스트) + 증거 요구**. [검증/2차]
3. 멀티에이전트는 토큰을 대략 15배 쓴다. 병렬화가 잘 되는 리서치에 맞고, **코딩처럼 의존성 높은 작업에는 맞지 않는 경우가 많다**고 Anthropic 스스로 말한다. 우리 15일 스프린트는 "얇은 수직 슬라이스"가 핵심이라 병렬 팬아웃은 **격리된 모듈 단위로만** 쓴다. [검증]

## 1. Anthropic 1차 출처

### 1.1 Building effective agents  [검증]
URL: https://www.anthropic.com/engineering/building-effective-agents
- 가장 단순한 해법부터. 복잡도는 성과가 확실히 좋아질 때만 추가. 대부분은 단일 LLM 호출 + 검색 + 예시로 충분할 수 있다.
- 프레임워크는 프롬프트/응답을 가려 디버깅을 어렵게 하니, API 직접 호출부터 시작하고 쓰더라도 내부를 이해할 것.
- 워크플로 패턴: 라우팅(분류 후 전문 처리, "쉬운 질문은 작은 모델로 어려운 건 큰 모델로"가 공식 예시), 오케스트레이터-워커(하위 작업을 미리 예측 못 할 때, 예: 몇 개 파일을 바꿔야 할지 모르는 코딩), 평가자-최적화자(평가 기준이 명확하고 반복 개선이 실제로 도움 될 때).
- 도구 설계(ACI)에 사람용 UI 만큼 공을 들일 것: 예시 사용법, 엣지 케이스, 입력 형식, 유사 도구와의 경계, 명확한 파라미터 이름. 실수하기 어렵게 만들기(poka-yoke): 상대경로 대신 절대경로 강제.
- 정지 조건(최대 반복 수 등)을 넣어 통제권 유지. 막히면 사람에게 체크포인트.
- 에이전트는 지연·비용을 성능과 맞바꾼다는 점을 항상 저울질.

### 1.2 멀티에이전트 리서치 시스템  [검증]
URL: https://www.anthropic.com/engineering/multi-agent-research-system
- 리드 Opus 4 + 서브에이전트 Sonnet 4가 단일 Opus 4보다 내부 리서치 평가에서 90.2% 높았다(당시 세대 모델 기준).
- 토큰: 에이전트는 채팅의 약 4배, 멀티에이전트는 약 15배. BrowseComp 성능 분산의 80%를 토큰 사용량이 설명. 그래서 가치 높은 작업에만.
- 위임 프롬프트에는 목표, 출력 형식, 도구/출처 가이드, 작업 경계가 필요. 모호하면 중복 작업 발생(한 에이전트는 2021 반도체 위기, 다른 둘은 같은 2025 공급망을 조사).
- 노력 스케일링 규칙을 프롬프트에 박을 것: 단순 사실 1에이전트 3~10호출, 비교 2~4에이전트, 복잡 10+. 초기 버전은 단순 질의에 50개 서브에이전트를 띄웠다.
- 평가: 실제 질의 약 20개로 시작해도 효과 크기가 보인다. LLM 판정(0~1 점수 + 합불)이 가장 일관. 사람 테스트가 자동 평가가 놓친 편향(SEO 콘텐츠팜 선호)을 잡았다.
- 실패 양상: 단순 작업에 과다 스폰, 없는 출처 무한 탐색, 충분한데 계속 진행, 너무 길고 구체적인 쿼리, 과도한 상태 업데이트가 다른 에이전트를 방해, 도구 설명이 나빠 잘못된 도구 선택.
- 도구 설명을 Claude가 직접 테스트하고 고쳐 쓰게 하면 이후 작업 시간이 40% 감소.
- 체크포인트/재개: 오류 시 처음부터 다시 하지 말고 실패 지점부터 재개. 결정적 안전장치(재시도, 정기 체크포인트) + 에이전트 적응의 병용. 리드가 계획을 메모리에 저장(컨텍스트 초과 시 잘림).
- 부적합: 모든 에이전트가 같은 컨텍스트를 요구하는 작업, 의존성 많은 작업, 대부분의 코딩, 15배 비용을 정당화 못 하는 저가치 작업.
- 병목: 리드가 가장 느린 서브에이전트를 동기 대기.

### 1.3 장시간 에이전트용 하네스  [검증]
URL: https://anthropic.com/engineering/effective-harnesses-for-long-running-agents
- 2단 구조: 초기화 에이전트(첫 세션 한 번) + 코딩 에이전트(이후 매 세션 점진 진행).
- 초기화 에이전트가 init.sh(개발 서버 기동), 진행 로그 파일, 최초 git 커밋을 만들고, 사용자 프롬프트를 포괄적 기능 목록으로 확장(claude.ai 클론 예: 200개 이상, 전부 실패 상태로 시작).
- 기능 목록은 **JSON**. Markdown보다 모델이 부적절하게 고치기 어려워서. 항목: category, description, 테스트 단계, passes(false 시작). 코딩 에이전트는 passes만 바꿀 수 있고, "테스트를 지우거나 고치는 건 용납 불가"라고 프롬프트에 명시.
- 진행 파일명 claude-progress.txt. git 이력과 함께 새 컨텍스트가 상태를 빠르게 파악.
- 코딩 에이전트는 **한 번에 한 기능**. 매 세션을 "main에 머지 가능한 상태"로 마무리. 설명적 커밋 메시지로 되돌리기 가능.
- 세션 시작 루틴: 작업 디렉터리 확인, git 로그와 진행 파일 읽기, 기능 목록 검토, 최우선 미완 기능 선택, init.sh로 기본 end-to-end 점검 후 새 작업.
- 검증은 브라우저 자동화로 사람처럼 end-to-end. 명시적으로 프롬프트해야 함. 한계: 네이티브 alert 모달은 안 보임.
- 실패와 처방 표: 조기 완료 선언 -> 기능 목록 + 한 기능씩 / 버그·미기록 진행 -> git + 진행 노트 + 시작 시 기본 테스트 / 기능 조기 완료 표시 -> 신중히 테스트한 뒤에만 passes / 실행법 헤매기 -> init.sh.

### 1.4 Claude Code 모범 사례  [검증]
URL: https://code.claude.com/docs/en/best-practices
- 최우선: 컨텍스트 윈도우는 가장 중요한 자원이고, 찰수록 성능이 떨어진다.
- "검증 수단을 줘라": 테스트/빌드/린터/스크린샷 비교. 검증이 있어야 사람이 지켜보지 않는 세션이 가능. 게이트 강도 사다리: 프롬프트 내 지시 < /goal 조건(별도 평가자가 매 턴 재확인) < **Stop 훅**(스크립트로 검증을 돌려 통과 전 종료 차단) < 검증 서브에이전트(새 모델이 반박 시도).
- 성공 주장 대신 **증거**(테스트 출력, 실행한 명령과 결과)를 요구.
- 탐색 -> 계획 -> 구현 -> 커밋. 한 문장으로 diff를 설명할 수 있으면 계획 생략.
- CLAUDE.md: 짧게. "이 줄을 빼면 실수하나?"로 가지치기. 너무 길면 규칙이 묻힌다. 반드시 지켜야 하는 건 CLAUDE.md(조언적)가 아니라 **훅(결정적)**. 가끔 쓰는 지식은 skill로.
- 서브에이전트: 별도 컨텍스트에서 조사하고 요약만 반환. 적대적 리뷰: 새 컨텍스트의 서브에이전트가 diff와 기준만 보고 갭을 보고. 단, 리뷰어는 지적거리를 만들어 내므로 "정확성/요구사항에 영향 주는 갭만" 보고하게 해야 과잉 설계를 피한다.
- 같은 문제를 두 번 넘게 교정했으면 /clear 후 더 나은 프롬프트로 재시작.
- 실패 패턴 5종: 키친싱크 세션, 반복 교정, 비대한 CLAUDE.md, 신뢰 후 검증 공백, 무제한 탐색.
- 병렬: 워크트리, 크로스 세션 메시징, 클라우드 세션, /batch(5~30 서브에이전트, 각자 워크트리). Writer/Reviewer 분리: 새 컨텍스트가 더 정확한 리뷰.
- 무인 실행 시 --allowedTools + dontAsk로 허용 범위 고정.

### 1.5 서브에이전트 레퍼런스  [검증]
URL: https://code.claude.com/docs/en/sub-agents
- frontmatter: name, description 필수. model은 sonnet/opus/haiku/fable/전체 ID/inherit. 해석 순서: 호출별 model > 정의 > CLAUDE_CODE_SUBAGENT_MODEL > 메인 모델.
- tools는 허용목록, disallowedTools는 거부목록(거부 먼저 적용). 생략하면 전부 상속이니 명시적으로 좁힐 것.
- isolation: worktree로 격리 복사본에서 작업. 기본 최대 동시 20개(환경 상한은 별도).
- 서브에이전트는 대화 이력을 못 본다. 위임 메시지가 곧 전부. 중첩 스폰 기본 3단까지, 필요 없으면 1로 끄기.
- 서브에이전트가 맞는 때: 장황한 출력 격리, 도구 제한, 자기완결 작업. 맞지 않는 때: 반복 왕복, 단계 간 컨텍스트 공유, 빠른 소수정.

### 1.6 컨텍스트 엔지니어링  [검증]
URL: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents
- 컨텍스트는 유한한 "주의력 예산"; 길수록 회상 저하(context rot).
- 압축(compaction): 한계 근처에서 요약해 새 윈도우로. 먼저 재현율을 극대화하고 그다음 정밀도로 다듬기.
- 구조화된 노트 작성: NOTES.md/TODO를 컨텍스트 밖에 저장하고 재개 시 읽기.
- 서브에이전트가 깨끗한 컨텍스트에서 일하고 1,000~2,000 토큰 요약만 반환.
- 적시(just-in-time) 검색: 경로/쿼리 같은 가벼운 참조만 들고 있다가 필요할 때 로드. 오래된 도구 결과 비우기가 가장 가벼운 압축.

### 1.7 비용 관리  [검증]
URL: https://code.claude.com/docs/en/costs
- 엔터프라이즈 평균 개발자당 활성일 약 $13, 90%가 $30 미만(2차 해석 주의: 사람이 쓰는 대화형 기준이며 무인 하네스와 다름).
- Sonnet으로 대부분의 코딩, Opus는 아키텍처·다단계 추론에. 단순 서브에이전트는 haiku 지정. 에이전트 팀은 대략 7배 토큰, 팀원은 Sonnet, 팀 소규모, 끝난 팀원 종료.
- 훅으로 로그를 사전 필터링(수만 토큰 -> 수백). CLAUDE.md는 200줄 이하, 특정 워크플로는 skill로.
- 사고 토큰은 출력 토큰으로 과금. Opus 5.5/Sonnet 5.5/Haiku 5.5/Fable은 사고를 끌 수 없으니 effort로 조절.
- 긴 세션은 캐시 만료(구독 1시간, API 기본 5분) 후 첫 메시지가 전체 재처리. 예약 작업·크로스 세션 메시지·goal 체크인도 전체 컨텍스트를 매번 보낸다. 서브에이전트/워크플로 에이전트는 각자 요청을 추가로 쓴다.

## 2. 모델 라우팅·캐스케이드: 실제 효과와 함정

### 2.1 근거
- RouteLLM(arXiv 2406.18665): 질의당 모델 하나로 라우팅, 벤치마크에서 비용 2배 이상 절감 보고. 캐스케이드와 달리 비용이 상담 모델 수에 비례하지 않는다. [2차: 검색 스니펫, 논문 본문 미확인] https://arxiv.org/html/2406.18665v2
- FrugalGPT: 싼 모델부터 순차 질의해 "믿을 만한 응답"이 나올 때까지 올라가는 캐스케이드. 일부 벤치마크에서 큰 절감 주장(수치는 해설 인용, 조건 미확인). [2차]
- 위 검색에서 흔히 도는 "85%를 싼 모델로 보내고 품질 95% 유지" 같은 숫자는 출처 불분명한 블로그 수치라 **채택하지 않는다**. [2차, 불신]
- Anthropic 공식: 쉬운 질문은 작은 모델로, 어려운 건 큰 모델로 라우팅은 유효한 패턴. 리드 Opus + 서브 Sonnet이 단일 Opus를 크게 이김(리서치 한정, 당시 세대). [검증]

### 2.2 함정 (우리 환경에 곧바로 적용)
1. **캐스케이드의 핵심 위험은 "싼 모델 답이 충분한가"의 판정 품질**이다. 싼 모델이 자기 결과를 자신 있게 틀리면 올라가지 않는다. 판정은 자기 보고가 아니라 실행 신호(테스트·CI)로 해야 한다. [2차 + 논리]
2. **프롬프트 캐시는 모델별 네임스페이스**(지시받은 확정 사실). 모델을 섞을수록 캐시 재사용을 잃는다. 긴 공통 접두(CLAUDE.md, 설계 문서)를 모델마다 따로 캐시 쓰기 비용으로 낸다.
3. **공식 비용 원칙**(지시받은 확정 사실): 캐스케이드를 짓기 전에 최강 모델을 낮은 effort로 같은 작업에 돌린 단순 기준선을 먼저 재고, 요청당이 아니라 **완료된 작업당 비용**으로 판단. 싼 모델이 3번 재시도하고 상위 모델이 고치면 총비용이 더 클 수 있다.
4. 관측성 없는 라우팅은 실패 패턴. 모델별 통과율·재시도 횟수·완료당 비용을 기록해야 한다. [2차]
5. 가격 비율 감각(확정 사실 기준): 출력 $/MTok = Fable 50, Opus 20, Sonnet 10, Haiku 0.5. Sonnet은 Opus의 절반, Haiku는 Sonnet의 1/20. 즉 **Opus와 Sonnet 사이는 2배일 뿐**이라, 재시도 2회면 이득이 사라진다. Haiku는 20배 차이라 분류·요약·체크리스트 대조처럼 틀려도 싼 일에 압도적으로 유리. Haiku는 100K 초과 프롬프트에서 단가가 5배라는 점도 주의.
6. Advisor 패턴(싼 실행자가 강한 조언자에게 묻는 공식 도구)은 캐스케이드보다 단순한 대안. 막혔을 때만 상위 호출. 단, 지금 우리 실행 환경(Workflow 도구)에서 이 도구를 쓸 수 있는지는 미확인.
7. Fable 5.1은 강제 tool_choice 불가, 한 턴이 수 분. 대화형 루프 안쪽이 아니라 **하루 몇 번의 게이트 심사**에만.

### 2.3 우리에게 맞는 라우팅 결론
- 라우팅은 "역할"로 고정(설계=Opus, 심사=Fable/Opus, 구현=Sonnet, 기계적 점검=Haiku)하고, "실패 시 승급" 규칙을 둔다: Sonnet 2회 실패 -> 같은 작업을 Opus가 원인 진단만(코드는 다시 Sonnet), 그래도 안 되면 Opus 직접 구현.
- 첫 주에 **단일 모델 기준선 실험**: 같은 슬라이스 작업 3개를 (a) Opus medium 단독 (b) Sonnet medium 구현 + Opus 심사로 돌려 완료당 비용·시간·재작업률을 비교하고 라우팅표를 갱신.

## 3. 오케스트레이터-워커 / 평가자-최적화자 (우리 적용 관점)

- 오케스트레이터-워커는 하위 작업이 사전에 예측 불가할 때. 우리는 슬라이스 설계가 있으므로 오케스트레이터(Opus)가 **작업 카드**를 만들고 워커(Sonnet)가 카드 하나씩 수행. 위임 카드에는 목표, 입출력 인터페이스, 수정 허용 파일 목록, 금지 사항(테스트 수정 금지), 완료 검증 명령, 예산 상한을 넣는다. [검증: 위임 요소]
- 코딩은 의존성이 커서 병렬 이득이 작다 [검증]. 병렬은 **파일 소유권이 겹치지 않는 모듈**(예: 개별 소형 모델 래퍼 14종 각각)과 워크트리 격리로만.
- 평가자-최적화자: 평가 기준이 명확할 때만. 평가자는 구현자와 다른 컨텍스트·다른(상위) 모델이어야 하고, 반복 상한(예: 3회)을 둔다. 리뷰어가 항상 흠을 찾아내므로 "정확성·요구사항 위반만" 보고하게 해 과잉 설계를 막는다. [검증]
- 미감 판정(영상 품질)은 자동 평가자로 대체 불가: 창업자 최종 판정 + 고정 입력 24장 A/B가 진짜 심판. LLM은 보조 점수.

## 4. 체크포인트·재개 / 컨텍스트 엔지니어링 적용
- 상태는 대화가 아니라 **레포 파일**: feature_list.json(passes만 수정 가능), progress.md, STATE.md, 작업 카드, git 커밋. 컨테이너가 수시로 리셋되므로 푸시되지 않은 것은 없는 것. [검증 + 프로젝트 사실]
- 세션 시작 루틴과 종료 루틴을 SessionStart/Stop 훅으로 강제(권고 아니라 결정적). [검증]
- 워크플로 resumeFromRunId는 같은 세션에서만 → 세션 간 재개는 파일 상태로.
- 서브에이전트에게 컨텍스트를 줄 땐 필요한 파일 경로와 인터페이스만. 결과는 1~2K 토큰 요약 + 증거(명령·출력 꼬리)로 반환받기. [검증]

## 5. 에이전트 코드 품질 게이트
- 테스트·빌드·린터·스크린샷 비교처럼 **에이전트가 읽을 수 있는 합불 신호**가 무인 실행의 전제. [검증]
- 게이트 사다리: (1) 프롬프트 지시 (2) /goal 평가자 (3) Stop 훅으로 종료 차단 (4) 새 컨텍스트 검증 서브에이전트 (5) GitHub Actions CI. 우리는 3~5를 다 쓴다. [검증 1~4]
- 테스트 우선: 위임 전에 상위 모델이 **수용 테스트(실패 상태)**를 먼저 쓰고, 구현자는 그걸 통과시키되 수정 금지. Anthropic 문서도 "한 Claude가 테스트를 쓰고 다른 Claude가 통과시키는 코드를 쓰는" 분리를 제안. [검증]
- 정적 검사(타입체크, 린트)는 편집 후 훅으로 자동 실행. 린터를 끄거나 any로 도망가는 우회가 실제로 보고됨. [검증: 훅 / 2차: 우회 사례]
- 리뷰: 작성자와 다른 새 컨텍스트. "정확성·요구사항 갭만". [검증]
- UI/시각 산출물은 스크린샷으로 비교하되, 영상 품질은 사람 판정. [검증: 스크린샷 비교 원칙]

## 6. 비용 통제 (우리 가격표 기준)
- 가격(지시된 확정 사실): 입력/출력 $/MTok = Fable 10/50, Opus 4/20, Sonnet 2/10, Haiku 0.1/0.5. 캐시 읽기는 모델별 약 $0.20~0.25(Haiku 없음). Batch 50% 할인(비동기).
- 레버 순서: (1) 컨텍스트 짧게(/clear, 서브에이전트 격리, 훅 사전 필터) (2) effort 낮추기(사고는 못 끔: Sonnet은 에이전트 코딩 medium부터 권장) (3) 캐시 친화적 고정 접두(같은 모델로 같은 접두 반복) (4) Batch: 즉시성이 필요 없는 대량 일(라벨링, 데이터 주조소 품질 분류, 야간 평가 채점) (5) 모델 다운시프트.
- 상한: 에이전트별 토큰/시간 예산, 워크플로 budget.spent() 점검, 작업 카드당 최대 시도 횟수. 에이전트 팀은 약 7배, 멀티에이전트 약 15배 토큰이므로 **동시성을 쓸 값어치가 있는 곳**만. [검증]
- 숨은 비용: 캐시 만료 후 첫 호출의 전체 재처리, 유휴 세션의 예약 작업·체크인이 매번 전체 컨텍스트를 전송, 압축 자체가 큰 요청. 매시간 모니터링 트리거는 **새 세션 방식 + 짧은 프롬프트**가 낫다(긴 세션에 바인딩하면 매시간 전체 컨텍스트 재전송). [검증: 비용 페이지의 해당 항목에서 추론]
- 지표는 요청당이 아니라 **완료된 작업당 비용**과 **재작업률**. (지시된 공식 원칙)

## 8. 우리 하네스에 바로 넣을 규칙 25개

역할 분담
1. **설계·심사는 Opus 5.5(medium~high), 구현은 Sonnet 5.5(medium), 기계적 점검·분류·요약은 Haiku 5.5, Fable 5.1은 일일 게이트(주간 아키텍처 결정, D6–7 수직 슬라이스 판정, 최종 릴리스 심사)에만 쓴다.** Fable은 한 턴이 수 분이고 tool_choice 강제가 안 되므로 루프 안쪽에 두지 않는다.
2. **모든 구현 작업은 Opus가 쓴 작업 카드(목표, 인터페이스, 수정 허용 파일, 금지 사항, 검증 명령, 시도 상한)로만 위임하고, 구현자는 카드 밖 파일을 수정하지 않는다.** 서브에이전트는 대화를 못 보므로 카드가 전부다.
3. **카드 하나는 한 번에 한 기능만 담고, diff 한 문장으로 설명되는 크기로 쪼갠다.**
4. **새 캐스케이드·새 모델 조합은 도입 전에 'Opus 낮은 effort 단독' 기준선과 완료당 비용·재작업률로 비교하고, 이기지 못하면 도입하지 않는다.**
5. **승급 규칙: 같은 카드에서 Sonnet이 2회 실패하면 Opus가 원인만 진단해 카드를 고쳐 다시 Sonnet에 주고, 그래도 실패하면 Opus가 직접 구현한다.**

상태와 재개
6. **진실의 원천은 레포 파일이다: feature_list.json(항목별 passes, 수정은 passes만), progress.md, ops/STATE.md. 대화 기억은 신뢰하지 않는다.**
7. **모든 에이전트 세션은 시작 시 STATE.md·progress.md·git log·feature_list를 읽고 init 점검(스모크 테스트)을 통과시킨 뒤에만 새 작업을 시작한다(SessionStart 훅).**
8. **모든 세션은 머지 가능한 상태로 끝내고, 작은 단위로 자주 커밋·푸시한다. 푸시되지 않은 작업은 존재하지 않는 것으로 취급한다(컨테이너 리셋).**
9. **세션 종료 시 progress.md에 한 일, 남은 일, 막힌 점, 다음 첫 명령을 한 단락으로 남긴다(Stop 훅이 누락을 차단).**
10. **중단된 작업은 실패 지점부터 재개하고, 처음부터 다시 하지 않는다. 워크플로 재개는 같은 세션에서만 가능하니 세션을 넘는 재개는 파일 상태로 한다.**

검증과 게이트
11. **'완료'는 에이전트의 말이 아니라 검증 명령의 종료 코드와 CI 결과로만 성립한다. 보고에는 실행한 명령과 출력 꼬리를 증거로 첨부해야 한다.**
12. **수용 테스트는 상위 모델이 구현 전에 먼저 쓰고(실패 상태 확인), 구현 에이전트는 테스트·픽스처·골든 입력·평가 스크립트를 수정·삭제할 수 없다(경로 쓰기 금지 PreToolUse 훅).**
13. **구현 에이전트에게 '명세가 모순이거나 불가능하다'를 보고하는 정식 출구를 주고, 그 경우 테스트를 우회하지 말고 중단하도록 지시한다.**
14. **검증은 구현자와 다른 새 컨텍스트의 심사자(Opus)가 diff와 카드만 보고 수행하며, '정확성·요구사항 위반·범위 밖 변경'만 보고하게 한다(스타일 지적 제외).**
